# Migration guide: v4 to v5

This guide describes the breaking changes introduced in **Mollie.Api v5** and how to migrate from v4.

> **Note:** More breaking changes will be added as they are introduced. This is the first one.

---

## 1. Result-type flow (replaces exceptions)

In v4, every client method threw a `MollieApiException` when the Mollie API returned an error. In v5, client methods no longer throw exceptions for API errors. Instead, every method returns a result object that you inspect to determine the outcome.

- Typed methods return `MollieResult<T>`.
- Void operations (e.g. delete, cancel) return the non-generic `MollieResult`.

Each result exposes:

| Property | Description |
|---|---|
| `Success` | Whether the request succeeded. |
| `Data` | The typed response payload (`T?`), available when `Success` is `true`. |
| `Error` | A `MollieErrorMessage` with `Status`, `Title`, and `Detail` when the request failed. |
| `RequestUrl` / `HttpMethod` / `HttpStatusCode` | Details about the request that was made. |
| `RequestBody` / `ResponseBody` | The raw request and response bodies. |

```csharp
// v4 - threw MollieApiException on error
try {
    PaymentResponse payment = await paymentClient.CreatePaymentAsync(paymentRequest);
    string checkoutUrl = payment.Links.Checkout.Href;
}
catch (MollieApiException ex) {
    // handle error
}

// v5 - returns a result
MollieResult<PaymentResponse> result = await paymentClient.CreatePaymentAsync(paymentRequest);

if (result.Success) {
    string checkoutUrl = result.Data.Links.Checkout.Href;
}
else {
    // result.Error contains the error details
}
```

> **Note:** Client methods no longer throw `MollieApiException`. Update any `catch (MollieApiException ...)` blocks to check `result.Success` / `result.Error` instead, or call `EnsureSuccess()` (see below).

### Keeping the exception-based flow with `EnsureSuccess()`

If you prefer the v4 behaviour, call `EnsureSuccess()` on the result. It throws a `MollieApiException` when the Mollie API returned an error.

- On `MollieResult<T>` it returns the response data (`T`).
- On the non-generic `MollieResult` it returns the result itself.

```csharp
try {
    PaymentResponse payment = (await paymentClient.CreatePaymentAsync(paymentRequest)).EnsureSuccess();
    string checkoutUrl = payment.Links.Checkout.Href;

    (await paymentClient.CancelPaymentAsync(payment.Id)).EnsureSuccess();
}
catch (MollieApiException ex) {
    // ex.Details contains the error details, ex.Result the full result
}
```

`MollieApiException` still lives in the `Mollie.Api.Client` namespace and still exposes the `MollieErrorMessage` via `Details`. New in v5 is the `Result` property, which gives access to the HTTP status code and the raw request and response bodies.

### Compiler warning for unused results (`MOLLIE001`)

Because API errors no longer throw, a call whose result is ignored fails silently. The `Mollie.Api` package therefore ships with a Roslyn analyzer that reports warning `MOLLIE001` when a `MollieResult` is not used:

```csharp
// warning MOLLIE001: the result is not used
await paymentClient.CancelPaymentAsync(paymentId);

// No warning: the result is inspected
MollieResult result = await paymentClient.CancelPaymentAsync(paymentId);
(await paymentClient.CancelPaymentAsync(paymentId)).EnsureSuccess();

// No warning: the result is discarded on purpose
_ = await paymentClient.CancelPaymentAsync(paymentId);
```

The analyzer needs no setup. To change its severity or turn it off, add the following to your `.editorconfig`:

```ini
dotnet_diagnostic.MOLLIE001.severity = error   # or: none
```

### What still throws

The rule is: **API errors come back as a result; everything else throws.**

Only an error response from the Mollie API (a non-success HTTP status code) is turned into a failed `MollieResult`. The following still throw an exception and are not wrapped in a result:

| Situation | Exception |
|---|---|
| A required argument is missing or invalid (e.g. an empty ID, or a link that does not point to the Mollie API) | `ArgumentException` / `ArgumentNullException` |
| An OAuth-only parameter (e.g. `profileId`, `testmode`) is used with an API key | `InvalidOperationException` |
| The request could not be completed (DNS failure, connection refused, timeout) | `HttpRequestException` / `TaskCanceledException` |
| The request was cancelled via the `CancellationToken` | `OperationCanceledException` |
| A successful response could not be deserialized | `JsonException` |

This means a `try`/`catch` around a client call is still useful for network failures, but you no longer need one to handle errors returned by Mollie.

## 2. `DateTime` properties are now `DateTimeOffset` (or `DateOnly`)

In v4, all date/time properties were `DateTime`. This caused two problems:

1. **Loss of timezone/offset info.** Mollie returns ISO 8601 timestamps (e.g. `2018-03-20T13:13:37+00:00`), but `DateTime` discards the offset unless you carefully manage `DateTimeKind`.
2. **Date-only fields were modeled as full timestamps.** Fields like `DueDate`, `StartDate`, `SignatureDate`, `ConsumerDateOfBirth`, and `ReleaseDate` are calendar dates (`yyyy-MM-dd`) with no time component.

In v5 these are split into two categories:

| Category | v4 | v5 |
|---|---|---|
| Full timestamps (e.g. `CreatedAt`, `PaidAt`, `ExpiresAt`) | `DateTime` | `DateTimeOffset` |
| Date-only fields (e.g. `DueDate`, `StartDate`, `SignatureDate`, `ConsumerDateOfBirth`, `ReleaseDate`, `NextPaymentDate`) | `DateTime` | `DateOnly` on **net8.0+**, `DateTime` on **netstandard2.0** |

- **`DateTimeOffset`** preserves the UTC offset Mollie sends.
- **`DateOnly`** is the correct type for a calendar date and serializes as `yyyy-MM-dd`, matching the API contract.

Because `DateOnly` doesn't exist on `netstandard2.0`, the date-only fields use conditional compilation. The wire format (`yyyy-MM-dd`) is identical on all target frameworks, so the **API contract is preserved**.

> **Note:** The public type of date-only fields differs by target framework (`DateOnly` on net8.0+, `DateTime` on netstandard2.0), so code written against one won't compile unchanged against the other.

## 3. `Amount` changes

There are three breaking changes to the `Amount` class:

### 1. `Amount` no longer rounds the value

In v4, `Amount` rounded the value to the currency's decimals before sending it to Mollie. For example, `new Amount("EUR", 10.005m)` was sent as `"10.01"`.

In v5, the value is never rounded. It is still formatted with the number of decimals Mollie expects for the currency (2 by default, 0 for `JPY` and `ISK`), but only by adding or removing zeros:

| You set | Sent to Mollie |
|---|---|
| `new Amount("EUR", 20)` | `"20.00"` |
| `new Amount("EUR", 20.0000m)` | `"20.00"` |
| `new Amount("JPY", 500.00m)` | `"500"` |
| `new Amount("EUR", 10.005m)` | `"10.005"` (not rounded, Mollie rejects it) |

A value with more significant decimals than the currency allows is sent as you set it, and Mollie returns an error result. If you relied on the rounding in v4, round the value yourself before creating the `Amount`:

```csharp
var amount = new Amount("EUR", Math.Round(value, 2));
```

### 2. The string constructor has been removed

The constructor that accepted a string value, `Amount(string currency, string value)`, has been removed. Use the decimal constructor instead:

```csharp
// v4
var amount = new Amount("EUR", "20.00");

// v5
var amount = new Amount("EUR", 20.00m);
```

### 3. `Value` is now a `decimal` (was `string`)

`Amount.Value` is now of type `decimal` instead of `string`. Any code that reads `Value` as a string must be updated to use the `decimal` value (or call `.ToString()` explicitly).

### Deserialization

The API returns the value as a JSON string (e.g. `"20.00"`). A custom converter parses that string back into a `decimal`, so response models continue to work unchanged.

## 4. Retry policy: `IAsyncPolicy` → resilience pipeline (`Microsoft.Extensions.Http.Resilience`)

The library no longer depends on the deprecated `Microsoft.Extensions.Http.Polly` package. It now uses **`Microsoft.Extensions.Http.Resilience` 10.8.0** and the modern Polly v8 pipeline model.

### What changed

| | v4 | v5 |
|---|---|---|
| Package | `Microsoft.Extensions.Http.Polly` | `Microsoft.Extensions.Http.Resilience` |
| `MollieOptions.RetryPolicy` | `IAsyncPolicy<HttpResponseMessage>?` | `Action<ResiliencePipelineBuilder<HttpResponseMessage>>?` |
| `MollieHttpRetryPolicies.TransientHttpErrorRetryPolicy()` | returns `IAsyncPolicy<HttpResponseMessage>` | returns `Action<ResiliencePipelineBuilder<HttpResponseMessage>>` |
| DI wiring | `AddPolicyHandler(...)` | `AddResilienceHandler("Mollie", ...)` |

> **Note:** Because `Microsoft.Extensions.Http.Polly` is no longer referenced, the Polly v7 packages it brought in transitively (`Polly`, `Polly.Extensions.Http`) are no longer included either. If your application uses Polly v7 types directly (e.g. `Policy<HttpResponseMessage>`, `HttpPolicyExtensions`), add those packages to your own project.

For the large majority of users nothing changes:

```csharp
builder.Services.AddMollieApi(options => {
    options.ApiKey = builder.Configuration["Mollie:ApiKey"];
    options.RetryPolicy = MollieHttpRetryPolicies.TransientHttpErrorRetryPolicy();
});
```

### Migrating a custom policy

If you assigned your own `IAsyncPolicy<HttpResponseMessage>` to `options.RetryPolicy`, rewrite it as a `ResiliencePipelineBuilder<HttpResponseMessage>` configuration action:

```csharp
// v4 - legacy Polly
options.RetryPolicy = Policy<HttpResponseMessage>
    .HandleResult(response => response.StatusCode == HttpStatusCode.TooManyRequests)
    .WaitAndRetryAsync(3, retryAttempt => TimeSpan.FromSeconds(Math.Pow(2, retryAttempt)));

// v5 - resilience pipeline (Polly v8)
options.RetryPolicy = builder => {
    builder.AddRetry(new HttpRetryStrategyOptions {
        MaxRetryAttempts = 3,
        BackoffType = DelayBackoffType.Exponential,
        Delay = TimeSpan.FromSeconds(1)
    });
};
```

> **Note:** `HttpPolicyExtensions.HandleTransientHttpError()` (from `Polly.Extensions.Http`) no longer exists. The built-in `MollieHttpRetryPolicies.TransientHttpErrorRetryPolicy()` handles network failures, HTTP 5xx and HTTP 408 (Request Timeout) responses.

### Retry timing and behaviour

The built-in `MollieHttpRetryPolicies.TransientHttpErrorRetryPolicy()` still retries 3 times by default and handles the same errors, but the timing has changed:

| | v4 | v5 |
|---|---|---|
| Delay between retries | 2s, 4s, 8s | 1s, 2s, 4s (exponential, starting at 1s) |
| Jitter | No | Yes (random variation is added to each delay) |
| `Retry-After` response header | Ignored | Respected (the delay from the header is used when present) |

If you depend on the exact v4 timing, configure your own pipeline via `options.RetryPolicy` (see above) and set `Delay`, `UseJitter` and `ShouldRetryAfterHeader` on `HttpRetryStrategyOptions` accordingly.

## 5. `VatRate` is now a `decimal` (was `string`)

The `VatRate` property on line items is now a `decimal` instead of a `string`. This affects:

| Model | v4 | v5 |
|---|---|---|
| `PaymentLine.VatRate` | `string?` | `decimal?` |
| `OrderLineRequest.VatRate` | `string` | `decimal` |
| `OrderLineUpdateRequest.VatRate` | `string?` | `decimal?` |
| `OrderLineResponse.VatRate` | `string` | `decimal` |
| `SalesInvoiceLine.VatRate` | `string` | `decimal` |

```csharp
// v4
VatRate = "21.00"

// v5
VatRate = 21.00m
```

The value is sent to Mollie exactly as you set it and is not rounded: `21m` is sent as `"21"`, while `21.00m` is sent as `"21.00"`. Mollie accepts both, as long as the rate has no more than two significant decimals (`21.555` is rejected).

## 6. `GetOrderRefundListAsync` returns `OrderRefundResponse`

`IRefundClient.GetOrderRefundListAsync` now returns a list of `OrderRefundResponse` instead of `RefundResponse`, matching the type returned by `CreateOrderRefundAsync`.

```csharp
// v4
ListResponse<RefundResponse> refunds = await refundClient.GetOrderRefundListAsync(orderId);

// v5
MollieResult<ListResponse<OrderRefundResponse>> result = await refundClient.GetOrderRefundListAsync(orderId);
```

---

## 7. `RoutingDestination` moved namespace

`RoutingDestination` is used by more than just the Payments API, so it moved from `Mollie.Api.Models.Payment` to `Mollie.Api.Models`. Update your `using` directives:

```csharp
// v4
using Mollie.Api.Models.Payment;

// v5
using Mollie.Api.Models;
```
